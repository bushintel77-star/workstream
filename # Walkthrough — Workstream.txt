# Walkthrough — Workstream

> A landscaping project management tool. Voice-first capture, AI-driven survey, costed outputs.
> Working codename: **Walkthrough**. Rename later.

-----

## 0. Thesis

One voice note, captured on site, becomes the source of truth for the entire job.

From a single recording plus an address, the system derives the survey (title, house footprint, garden area, boundary measurements), the design (full proposal, gap-filled refinement, or pure validation depending on the brief), the costing, and every downstream artifact: task list, crew schedule, scope document, client quote letter, brochure.

No surveyor visit. No drafting back-and-forth before pricing. No re-keying between estimating, scheduling, and client comms. The walkthrough *is* the brief.

-----

## 1. Three Operating Modes

The same pipeline runs in three modes, branched on what the user provided.

|Mode             |Input                   |Behaviour                                                                                             |
|-----------------|------------------------|------------------------------------------------------------------------------------------------------|
|**Auto-design**  |Address only, no voice  |AI proposes a full design from site conditions, lot geometry, orientation, and Curtis & Co house style|
|**Gap-fill**     |Address + partial voice |AI honours every specified element, flags omissions, proposes fills for each gap with rationale       |
|**Validate-only**|Address + complete voice|AI checks coherence, costs the design, runs the self-audit, generates outputs                         |

The user is never forced to choose a mode. The system detects coverage from the transcript and selects automatically. A toggle on the design review screen lets the user override.

## 2. UX Flow (Mobile, End-to-End)

### 2.1 Screen inventory

1. **Home** — project list, new project CTA
1. **New project** — address entry, optional voice capture
1. **Recording** — full-screen dictation
1. **Processing** — survey + transcription progress
1. **Survey review** — aerial with title overlay, garden area, measurements
1. **Design review** — proposal, gap flags, mode indicator
1. **Cost review** — line items, totals, scenario toggle
1. **Audit** — self-audit findings, blocking issues, advisories
1. **Outputs** — generate task list / schedule / quote / brochure
1. **Project detail** — full project record, version history
1. **Settings** — rate card, plant palette, materials catalogue, crew

### 2.2 Happy path (voice + address)

```
Home
 └─ + New project
     └─ Enter address → autocomplete (Google Places, AU restricted)
         └─ Confirm pin on aerial
             └─ Start recording (or skip)
                 └─ Record walkthrough (max 30 min)
                     └─ Stop → upload
                         └─ Processing screen (survey + transcription run in parallel)
                             └─ Survey review (boundary, house cut-out, garden area, edge measurements)
                                 └─ Design review (proposal + gap flags + mode badge)
                                     └─ Cost review (Lean / Standard / Buffer scenarios)
                                         └─ Audit (must clear blocking issues to proceed)
                                             └─ Outputs (pick artefacts to generate)
                                                 └─ Share / export
```

Every step from Processing onward is **resumable**. The user can leave and the project sits at its current state on the home screen.

### 2.3 Recording screen — the most important screen

- Full-bleed surface
- One large record button (single tap to start, hold for waveform feedback)
- Live transcription strip at the top, scrolling, low-emphasis
- Elapsed time prominent, centered top
- A single tertiary action: “Pause”
- No other UI. No menus. No back button while live. (Confirm-to-cancel only.)

Rationale: the user is walking a site, hands sometimes dirty, attention split. The screen must tolerate accidental touches, glove use, and bright sun.

### 2.4 Survey review — the magic moment

This is where the user sees the AI has *understood the site*. It must feel correct on first read.

Layout: aerial fills the upper two-thirds. Title boundary drawn as a 2px sharp line. House footprint subtracted, shown as a darker silhouette. Garden polygon highlighted with the accent at 12% opacity. Edge measurements rendered along each boundary segment in mono.

Lower third: a single summary card.

```
Lot          624 m²
House         168 m²
Garden        456 m²
Frontage       15.2 m
Depth          41.1 m
```

One CTA: “Looks right →”. One secondary: “Adjust” (opens a corrections sheet for boundary nudging — rare).

### 3.3 Component primitives

- **Button** — primary (accent fill), secondary (line strong border), tertiary (text only). 48px tap target minimum.
- **Field** — bottom-line input on `--surface-sunken`, label sits above in `micro` uppercase.
- **Card** — `--surface-elevated`, `--radius-lg`, `--elev-1`, `--space-5` padding.
- **Sheet** — bottom sheet for any flow that returns the user to the previous screen. Full screen for any flow that progresses them.
- **Metric** — `caption` micro label uppercase, value in `display-m` mono. Used everywhere a number appears.
- **Flag** — pill-shaped, semantic colour, used for gap flags, audit findings, mode badges.

### 3.4 Dark mode

The recording screen and the survey overlay are dark-mode native (always rendered on `--surface-inverted`). The rest of the app respects system preference. Same token names, swapped values.

### 4.4 Land.vic integration — the unknown

Land.vic.gov.au exposes property data via the **Property and Parcel Search** and **Vicmap** services. Three options, in order of preference:

1. **Vicmap Property Polygon WFS** — official spatial service. Returns parcel polygons as GeoJSON given a lat/lng or address. Requires Vicmap subscription (free for some tiers, paid for commercial use). **Verify licensing before launch.**
1. **PSMA / Geoscape G-NAF + Cadastre** — national property dataset. Paid, but well-documented and stable. Probably the right answer for a commercial product.
1. **Scrape** — last resort. Land.vic’s public viewer renders polygons client-side; reverse-engineering is possible but fragile and likely against ToS. Don’t ship this.

**Action**: Phase 0 spike to confirm Vicmap licensing for commercial use. If blocked, switch to Geoscape from day one. Either way, the system never depends on a scrape in production.

### 4.5 House footprint

Two approaches, run in series:

1. **Google Maps Building Insights** — where available, returns a building polygon. Free tier exists. Try first.
1. **Vision fallback** — Claude vision (or a fine-tuned segmentation model) reads the aerial and segments roofs. Run only if Building Insights returns nothing.

Subtract house polygon from title polygon using Turf.js (`turf.difference`). The result is the garden polygon. Measurements are computed off the garden polygon edges.

## 5. Automation Pipeline

End-to-end, the pipeline runs as a sequence of idempotent stages on the worker. Each stage writes to Postgres and emits a WebSocket event the mobile app subscribes to.

```
[1]  Capture          recording uploaded → audio_uri persisted
[2]  Transcribe       Whisper → transcript + confidence
[3]  Geocode          address → lat/lng (validated)
[4]  Aerial           Google Maps Static → aerial_uri
[5]  Title            Vicmap/Geoscape → title polygon (geojson)
[6]  House            Building Insights or vision → house polygon
[7]  Garden           turf.difference → garden polygon + areas
[8]  Measure          edge measurements, frontage, depth, key lines
[9]  Mode detect      analyse transcript coverage → auto|gapfill|validate
[10] Design           Claude → proposal (zones, planting, hardscape, lighting)
[11] Gap flag         Claude → explicit gaps with proposed fills
[12] Cost             rate card + plant palette + line items → 3 scenarios
[13] Audit            self-audit pass (see §6.2)
[14] Outputs          generated on demand from the design + costing
```

Stages 1–8 run in parallel where possible. Stages 9–14 are sequential and depend on the artefacts upstream. A failure in any stage halts the pipeline at that point and surfaces a recoverable error state to the user.

## 6. Guardrails and Self-Audit

### 6.1 Guardrails (pre-flight, prevent bad data entering the pipeline)

- **Address must geocode to a single AU result.** Ambiguous → user confirms on a map.
- **Aerial must be ≥ 18 zoom.** Otherwise re-fetch at higher zoom or abort with a clear error.
- **Title polygon must close.** Open polygons reject the survey.
- **Title area must be 100 m² ≤ A ≤ 50,000 m².** Outside that range, flag for manual review.
- **House polygon must be 15% ≤ H/T ≤ 70% of title.** Outside, flag (might be an apartment, vacant lot, or detection error).
- **Garden area must be ≥ 20 m².** Below, the tool isn’t useful — surface a friendly message.
- **Transcription confidence must be ≥ 0.85 average.** Below, prompt the user to re-record or proceed with caution.
- **Plant species must exist in the palette or in a known Melbourne climate-tolerant list.** Unknown species generate a gap flag, never silent failure.
- **Cost line items must have an SKU match on the rate card.** No match → flag as “estimate only”.
- **Quote totals must be within ±25% of Curtis & Co historical median for similar lot size.** Outside, flag for manual review before client send.

### 6.2 Self-audit (post-design, validates the AI’s own work)

After the design and costing are generated, a separate Claude pass runs the audit. It receives the full transcript, the design proposal, the gap flags, and the costing. It returns a structured findings list.

```
Audit findings shape:
  - severity: blocking | advisory
  - category: fidelity | completeness | coherence | cost | safety | scope
  - location: zone / line item / boundary segment
  - statement: human-readable finding
  - suggested_action: literal next step the user can take
```

Categories:

- **Fidelity** — does the design honour what the user said? (“Voice mentions a pleached hornbeam screen along the west boundary; design shows mixed natives. Reconcile.”)
- **Completeness** — are there zones with no treatment? (“North-east corner has no planting or hardscape specified.”)
- **Coherence** — does the design contradict itself? (“Pergola structure specified but no footings in line items.”)
- **Cost** — are totals internally consistent? (“Standard scenario excludes irrigation but design includes drip lines.”)
- **Safety** — anything dangerous? (“Retaining wall >1.0m specified, no engineering allowance noted.”)
- **Scope** — is the proposal in or out of Curtis & Co’s stated capabilities? (“Concrete pool specified — outside scope. Refer to specialist.”)

**Blocking findings prevent output generation.** The user must resolve or explicitly override (with a recorded reason). Advisories are shown but do not block.

### 6.3 The override ledger

Every override is recorded against the project. The audit page on the project detail screen shows the full history. This is the equivalent of an immutable diary — what was flagged, what was overridden, by whom, when, why. It exists so that a job that goes sideways six months later has a reconstructible record.

- Plant palette management

- Cost review screen

Exit criteria: design + rate card → three costed scenarios that pass internal review against Curtis & Co historical pricing.

### Phase 5 — Audit (Week 6)

- Blocking vs advisory enforcement
- Override ledger

Exit criteria: audit pass runs on every project, surfaces blocking issues correctly on a deliberately broken test case, allows override with reason logged.

### Phase 6 — Outputs (Week 7)

- Client quote letter (branded PDF, Curtis & Co letterhead)
- Scope document (internal PDF)

Exit criteria: a complete project, end-to-end, produces all five artefacts.

### Phase 7 — Crew (Week 8–9)

- Crew accounts, assignments per task
- Mobile task view for crew, check-in / check-out

Exit criteria: one real Curtis & Co job runs through the system from walkthrough to crew completion.

### Phase 8 — Client portal (Week 10–11)

- Magic-link client login (no signup)
- Live quote view, accept / request changes

Exit criteria: one client signs a quote and pays a deposit through the portal.

### Phase 9 — Hardening (Week 12)

- Plant palette validated against Melbourne climate zones
- Override ledger UI polish

## 9. Risks (called early, not at the end)

- **Title data licensing.** Single biggest risk. Spike in Phase 0, not later.
- **Building Insights coverage in Melbourne.** Some suburbs have it, some don’t. Vision fallback must work on day one, not as a Phase 9 nice-to-have.
- **Transcription quality outdoors.** Wind, traffic, generator noise. The recording screen should test microphone gain and warn if ambient noise is high.
- **AI design plausibility.** The first two or three auto-designs will be wrong in instructive ways. Don’t ship to clients in Phase 3. Internal use only until Phase 6.
- **Rate-card drift.** If pricing isn’t kept current, the costing engine generates confident garbage. Make rate-card updates a first-class flow, not a settings afterthought.
- **Liability on engineering items.** Retaining walls, drainage, anything structural — the audit must flag these out to a qualified engineer. Don’t let the AI quote them.

-----

## 10. Out of Scope (explicit)

- Web app. Mobile only until Phase 9 ships.
- iPad layout. Phone-only initially.
- Multi-language. English AU only.
- Non-Victoria properties. NSW/QLD title data needs separate integrations.
- Pools, structural engineering, swimming-pool fencing certification.
- Plan-view drafting. Drafting stays with the draftsperson. The app produces brief, costing, and schedule — not survey-grade drawings.

The last point is non-negotiable and matches the division of labour you’ve already set with Curtis & Co.

# Walkthrough — Workstream

> A landscaping project management tool. Voice-first capture, AI-driven survey, costed outputs.

## 0. Thesis

One voice note, captured on site, becomes the source of truth for the entire job.

From a single recording plus an address, the system derives the survey (title, house footprint, garden area, boundary measurements), the design (full proposal, gap-filled refinement, or pure validation depending on the brief), the costing, and every downstream artifact: task list, crew schedule, scope document, client quote letter, brochure.

No surveyor visit. No drafting back-and-forth before pricing. No re-keying between estimating, scheduling, and client comms. The walkthrough *is* the brief.

-----

## 1. Three Operating Modes

The same pipeline runs in three modes, branched on what the user provided.

|Mode             |Input                   |Behaviour                                                                                             |
|-----------------|------------------------|------------------------------------------------------------------------------------------------------|
|**Auto-design**  |Address only, no voice  |AI proposes a full design from site conditions, lot geometry, orientation, and Curtis & Co house style|
|**Gap-fill**     |Address + partial voice |AI honours every specified element, flags omissions, proposes fills for each gap with rationale       |
|**Validate-only**|Address + complete voice|AI checks coherence, costs the design, runs the self-audit, generates outputs                         |

The user is never forced to choose a mode. The system detects coverage from the transcript and selects automatically. A toggle on the design review screen lets the user override.

### 4.4 Land.vic integration — the unknown

Land.vic.gov.au exposes property data via the **Property and Parcel Search** and **Vicmap** services. Three options, in order of preference:

1. **Vicmap Property Polygon WFS** — official spatial service. Returns parcel polygons as GeoJSON given a lat/lng or address. Requires Vicmap subscription (free for some tiers, paid for commercial use). **Verify licensing before launch.**
1. **PSMA / Geoscape G-NAF + Cadastre** — national property dataset. Paid, but well-documented and stable. Probably the right answer for a commercial product.
1. **Scrape** — last resort. Land.vic’s public viewer renders polygons client-side; reverse-engineering is possible but fragile and likely against ToS. Don’t ship this.

**Action**: Phase 0 spike to confirm Vicmap licensing for commercial use. If blocked, switch to Geoscape from day one. Either way, the system never depends on a scrape in production.

### 4.5 House footprint

Two approaches, run in series:

1. **Google Maps Building Insights** — where available, returns a building polygon. Free tier exists. Try first.
1. **Vision fallback** — Claude vision (or a fine-tuned segmentation model) reads the aerial and segments roofs. Run only if Building Insights returns nothing.

Subtract house polygon from title polygon using Turf.js (`turf.difference`). The result is the garden polygon. Measurements are computed off the garden polygon edges.

## 5. Automation Pipeline

End-to-end, the pipeline runs as a sequence of idempotent stages on the worker. Each stage writes to Postgres and emits a WebSocket event the mobile app subscribes to.

```
[1]  Capture          recording uploaded → audio_uri persisted
[2]  Transcribe       Whisper → transcript + confidence
[3]  Geocode          address → lat/lng (validated)
[4]  Aerial           Google Maps Static → aerial_uri
[5]  Title            Vicmap/Geoscape → title polygon (geojson)
[6]  House            Building Insights or vision → house polygon
[7]  Garden           turf.difference → garden polygon + areas
[8]  Measure          edge measurements, frontage, depth, key lines
[9]  Mode detect      analyse transcript coverage → auto|gapfill|validate
[10] Design           Claude → proposal (zones, planting, hardscape, lighting)
[11] Gap flag         Claude → explicit gaps with proposed fills
[12] Cost             rate card + plant palette + line items → 3 scenarios
[13] Audit            self-audit pass (see §6.2)
[14] Outputs          generated on demand from the design + costing
```

Stages 1–8 run in parallel where possible. Stages 9–14 are sequential and depend on the artefacts upstream. A failure in any stage halts the pipeline at that point and surfaces a recoverable error state to the user.

## 6. Guardrails and Self-Audit

### 6.1 Guardrails (pre-flight, prevent bad data entering the pipeline)

- **Address must geocode to a single AU result.** Ambiguous → user confirms on a map.
- **Aerial must be ≥ 18 zoom.** Otherwise re-fetch at higher zoom or abort with a clear error.
- **Title polygon must close.** Open polygons reject the survey.
- **Title area must be 100 m² ≤ A ≤ 50,000 m².** Outside that range, flag for manual review.
- **House polygon must be 15% ≤ H/T ≤ 70% of title.** Outside, flag (might be an apartment, vacant lot, or detection error).
- **Garden area must be ≥ 20 m².** Below, the tool isn’t useful — surface a friendly message.
- **Transcription confidence must be ≥ 0.85 average.** Below, prompt the user to re-record or proceed with caution.
- **Plant species must exist in the palette or in a known Melbourne climate-tolerant list.** Unknown species generate a gap flag, never silent failure.
- **Cost line items must have an SKU match on the rate card.** No match → flag as “estimate only”.
- **Quote totals must be within ±25% of Curtis & Co historical median for similar lot size.** Outside, flag for manual review before client send.

### 6.2 Self-audit (post-design, validates the AI’s own work)

After the design and costing are generated, a separate Claude pass runs the audit. It receives the full transcript, the design proposal, the gap flags, and the costing. It returns a structured findings list.

```
Audit findings shape:
  - severity: blocking | advisory
  - category: fidelity | completeness | coherence | cost | safety | scope
  - location: zone / line item / boundary segment
  - statement: human-readable finding
  - suggested_action: literal next step the user can take
```

Categories:

- **Fidelity** — does the design honour what the user said? (“Voice mentions a pleached hornbeam screen along the west boundary; design shows mixed natives. Reconcile.”)
- **Completeness** — are there zones with no treatment? (“North-east corner has no planting or hardscape specified.”)
- **Coherence** — does the design contradict itself? (“Pergola structure specified but no footings in line items.”)
- **Cost** — are totals internally consistent? (“Standard scenario excludes irrigation but design includes drip lines.”)
- **Safety** — anything dangerous? (“Retaining wall >1.0m specified, no engineering allowance noted.”)
- **Scope** — is the proposal in or out of Curtis & Co’s stated capabilities? (“Concrete pool specified — outside scope. Refer to specialist.”)

**Blocking findings prevent output generation.** The user must resolve or explicitly override (with a recorded reason). Advisories are shown but do not block.

### 6.3 The override ledger

Every override is recorded against the project. The audit page on the project detail screen shows the full history. This is the equivalent of an immutable diary — what was flagged, what was overridden, by whom, when, why. It exists so that a job that goes sideways six months later has a reconstructible record.

## 9. Risks (called early, not at the end)

- **Title data licensing.** Single biggest risk. Spike in Phase 0, not later.
- **Building Insights coverage in Melbourne.** Some suburbs have it, some don’t. Vision fallback must work on day one, not as a Phase 9 nice-to-have.
- **Transcription quality outdoors.** Wind, traffic, generator noise. The recording screen should test microphone gain and warn if ambient noise is high.
- **AI design plausibility.** The first two or three auto-designs will be wrong in instructive ways. Don’t ship to clients in Phase 3. Internal use only until Phase 6.
- **Rate-card drift.** If pricing isn’t kept current, the costing engine generates confident garbage. Make rate-card updates a first-class flow, not a settings afterthought.
- **Liability on engineering items.** Retaining walls, drainage, anything structural — the audit must flag these out to a qualified engineer. Don’t let the AI quote them.

-----

## 10. Out of Scope (explicit)

- Web app. Mobile only until Phase 9 ships.
- iPad layout. Phone-only initially.
- Multi-language. English AU only.
- Non-Victoria properties. NSW/QLD title data needs separate integrations.
- Pools, structural engineering, swimming-pool fencing certification.
- Plan-view drafting. Drafting stays with the draftsperson. The app produces brief, costing, and schedule — not survey-grade drawings.

The last point is non-negotiable and matches the division of labour you’ve already set with Curtis & Co.

### B.13 Notes for the costing engine

- Three scenarios pull from the **same** design but different rate-card subsets. Lean strips lighting wash, irrigation upgrades, and the contingency. Buffer adds engineering allowances by default, upgrades pleach stock by one size, and uses the 8% contingency.
- Plant stock SKUs (B.2) take precedence over generic pot-size SKUs (B.1) when a species match exists. The generic SKUs are the fallback for species in the palette but without a specific stock entry.
- POA items never appear silently in a total. The costing engine surfaces them as a separate “Provisional” section the user must resolve before quote generation.
- Rates are stored with an `effective_from` date. The costing engine always uses the rate effective on the project’s `created_at`. This protects historical projects from rate drift.
